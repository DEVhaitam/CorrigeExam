# Experiment Results — Analysis & Interpretation
## CorrectExam IaC Provisioning Study (Grid5000, parasilo-8)

---

## Context and Experimental Setup

The experiment deploys a full containerised instance of CorrectExam (Quarkus backend,
MySQL 8, MinIO, Angular frontend) inside a KVM virtual machine on a bare-metal Grid5000
node (32 cores, 128 GB RAM, parasilo-8.rennes.grid5000.fr).

Eight VM configurations were tested, varying two independent dimensions:

| Axis | Configurations |
|------|----------------|
| RAM (fixed 2 vCPUs) | 512 MB, 1 GB, 2 GB, 4 GB, 8 GB |
| CPU (fixed 4 GB RAM) | 1, 2, 4, 8 vCPUs |

Load is generated by Locust running scenario s03_mixed (mixed read/write: course listing,
exam browsing, grading, student lookup). Each load step runs for 5 minutes at a fixed
number of concurrent users: 10 → 25 → 50 → 100 → 200 → 500 → 1000 → 2000.

**Partial runs:** the 18-hour Grid5000 reservation expired before all configurations
completed their full sweep. Configs affected: 2cpu-8gb, 1cpu-4gb, 4cpu-4gb, 8cpu-4gb.
Results for these are reported as lower bounds (≥) on figures that show capacity.

**Failed to start:** 2cpu-512mb and 2cpu-1gb could not initialise the container stack at
all — the Linux OOM killer terminated MySQL before it could complete InnoDB
initialisation. These are not shown in the figures but are a finding in themselves.

## Figure-by-Figure Interpretation

---

### Fig 1 — Throughput vs. Concurrent Users (RAM Effect)
**File:** fig1_throughput_ram.png

**What it shows:** Throughput (requests per second) as a function of concurrent user
count, comparing the three 2-vCPU configurations with different RAM allocations: 2 GB,
4 GB, and 8 GB. Both axes are log-scaled.

**How to read it:** Each line is a configuration. Crosses (×) mark flagged data points
(reservation ended mid-test or VM crashed on load — exclude from trend analysis).
A rising line means the system is still absorbing more load. A flat or falling line
means the system has saturated.

**What the data shows:**
- The 2 GB and 4 GB curves are nearly indistinguishable from u10 to u500. Both reach
  ~200 req/s at 500 users.
- Only 2cpu-4gb has data beyond u500 (the reservation for 2cpu-2gb ended there). At
  u1000 throughput stays near 200 req/s, then drops to ~147 req/s at u2000 as the
  request queue overwhelms the server.
- The 8 GB line stops at u25 (reservation ended); its two valid points match the others.

**Potential conclusions:**
Doubling RAM from 2 GB to 4 GB does not improve throughput at the same CPU count —
both configurations deliver an identical scaling curve up to the point where we have
comparable data. The performance ceiling (~200 req/s) is determined by the vCPU count
and the application's I/O characteristics, not the available memory. Extra RAM appears
to extend survivability at higher load (2cpu-4gb survived to u2000 where 2cpu-2gb was
not tested), but this needs confirmation in the next reservation.

---

### Fig 2 — p95 Latency vs. Concurrent Users (RAM Effect)
**File:** fig2_latency_ram.png

**What it shows:** 95th-percentile response time in milliseconds (log scale) against
concurrent user count, for the same three 2-vCPU configurations. The red dashed line
marks the 1-second SLO (Service Level Objective) used as the saturation threshold.

**How to read it:** Below the red line = acceptable latency. The point where a curve
crosses the 1 s line indicates where this configuration begins to degrade for end users.

**What the data shows:**
- All three configurations maintain p95 below 100 ms up to ~25–50 users — the system
  is comfortably underloaded in that region.
- p95 rises steeply after u200. The 2 GB config crosses the 1 s SLO around u500
  (p95 = 1100 ms); the 4 GB config stays just below at u500 (p95 = 830 ms).
- At u1000, 2cpu-4gb reaches ~4 s; at u2000 it reaches ~57 s (queue saturation).
- The 8 GB data is insufficient to compare (only u10 and u25 are valid).

**Potential conclusions:**
4 GB RAM buys roughly one more load step of acceptable latency compared to 2 GB (stable
up to ~500 users vs. ~200 users). The shape of the degradation curve is identical — RAM
delays the crossing of the SLO threshold rather than fundamentally changing the
application's behaviour under load.

---

### Fig 3 — Throughput vs. Concurrent Users (CPU Effect)
**File:** fig3_throughput_cpu.png

**What it shows:** Throughput curves for the four 4-GB-RAM configurations with 1, 2, 4,
and 8 vCPUs respectively.

**What the data shows:**
- All four lines overlap almost exactly from u10 to u100. The system delivers 5 req/s
  at 10 users, 12 at 25, 23 at 50, and 47 at 100 — regardless of how many vCPUs are
  provisioned.
- Only 2cpu-4gb extends beyond u100. The other configurations were cut short by the
  reservation.

**Potential conclusions:**
This is one of the most important findings. For this workload, throughput is essentially
CPU-independent at equivalent user counts. The application's bottleneck is not
computation — it is database I/O latency. Quarkus uses a blocking JDBC executor pool
for Hibernate operations; each query occupies a thread and waits. Adding vCPUs creates
more threads but they all queue on the same MySQL instance, which is the true bottleneck.
This is a strong argument for the IaC paper: naively over-provisioning CPU does not
improve performance and wastes cost.

---

### Fig 4 — p95 Latency vs. Concurrent Users (CPU Effect)
**File:** fig4_latency_cpu.png

**What it shows:** p95 latency curves for the same four CPU configurations. Useful to
detect whether different CPU counts affect latency distribution.

**What the data shows:**
- At low load (u10–u50), all configs stay in the 60–130 ms range for p95. The 1-vCPU
  configuration is slightly higher at u50 (p95 ≈ 130 ms vs. ~60 ms for 2, 4, 8 vCPU),
  the first hint that a single core creates scheduling pressure.
- At u100, 1cpu-4gb crashes (flagged cross at ~68 000 ms — VM was destroyed). 8cpu-4gb
  remains at 59 ms at u100, then crashes at u200 (flagged).
- The crashes are due to the reservation ending (VM was torn down), not resource
  exhaustion — this will be confirmed when configurations are retested.

**Potential conclusions:**
A single vCPU begins to show latency pressure at 50 users, making it the only CPU
configuration where provisioning visibly hurts latency at the measured load levels.
Beyond 2 vCPUs, additional cores do not reduce latency. The full CPU experiment requires
the next reservation to extend the 4-vCPU and 8-vCPU curves to u200+ before a definitive
statement can be made.

---

### Fig 5 — Saturation Profile (2 vCPU / 4 GB RAM — Full Curve)
**File:** fig5_saturation_2cpu4gb.png

**What it shows:** Two-panel figure for the most completely tested configuration. Top
panel: throughput curve across all 8 user-count steps. Bottom panel: response-time
percentile fan (p50, p75, p95, p99) across the same steps, log-scaled.

**How to read it:** This is the reference configuration. The throughput curve shows the
system's capacity ceiling. The percentile fan shows the latency distribution widening as
the system approaches and passes saturation.

**What the data shows:**
- Throughput grows roughly linearly with concurrent users up to ~500, peaks at ~200 req/s
  (both at u500 and u1000 — a plateau), then drops to 147 req/s at u2000.
- The plateau-then-drop shape is classic queueing theory: the system is at 100% CPU
  utilisation, queueing requests. More users means more queue length, not more
  throughput. Eventually, timeout-related failures reduce even the completion rate.
- The percentile fan shows a clear inflection around u500:
  - p50 stays near 10 ms up to u200, then jumps to ~70 ms at u500 and ~1500 ms at u1000.
  - p95 is at 60–120 ms through u200, crosses 1 s at u500 (830 ms — just under), and
    reaches 4.5 s at u1000 and 57 s at u2000.
  - p99 crosses 1 s already at u100, indicating that even at moderate load the tail is
    affected by authentication bottleneck (see Fig 7).
- No HTTP failures are recorded at any step (0% failure rate throughout) — the system
  degrades gracefully with high latency rather than dropping requests.

**Potential conclusions:**
The saturation point for 2cpu-4gb is approximately 500 concurrent users. Below 200 users
the system provides a smooth, sub-100 ms experience at p95. The p99 tail is elevated
even at moderate loads due to the authentication endpoint (discussed in Fig 7). The
experiment confirms that the system does not hard-fail under overload — a positive quality
for production use — but degrades into unusably high latency beyond its capacity.

---

### Fig 6 — Response-Time Percentiles at 50 Concurrent Users
**File:** fig6_percentile_bars.png

**What it shows:** Grouped bar chart comparing five percentiles (p50, p75, p90, p95, p99)
across four configurations at a fixed moderate load of 50 concurrent users. (Note:
2cpu-8gb and 4cpu-4gb are absent because their u50 data was flagged as unreliable.)

**What the data shows:**
- p50 is consistently ~8 ms across all four shown configurations — the typical response
  is fast for all provisioning levels at this load.
- p90 and p95 are comparable: ~50–75 ms for 2cpu-2gb and 2cpu-4gb, ~60–130 ms for 1cpu-4gb.
- p99 diverges sharply: 1cpu-4gb has a p99 of ~530 ms, compared to ~190–200 ms for the
  2-vCPU configs and ~120 ms for 8cpu-4gb.
- The 1-CPU configuration's high p99 (but still fast p50) indicates single-threaded
  contention: most requests complete quickly but a minority queue behind each other.

**Potential conclusions:**
At 50 users, all configurations are well within acceptable latency for the median
request. The p99 tail is the discriminating metric: single-vCPU provisioning degrades
the worst 1% of requests significantly compared to 2+ vCPUs. For a real deployment
where SLO compliance is measured at p99, 1 vCPU is insufficient at this load level.

---

### Fig 7 — Per-Endpoint Latency Breakdown (2 vCPU / 4 GB, 100 and 500 users)
**File:** fig7_endpoint_breakdown.png

**What it shows:** Horizontal bar chart of p50 and p95 response time for the 12 slowest
API endpoints, at 100 and 500 concurrent users for the 2cpu-4gb configuration.

**What the data shows:**
- At 100 users: POST /api/authenticate takes ~5.2 s p50 and ~7.8 s p95. Every other
  endpoint is below 500 ms at p95. The authentication endpoint is 10–15x slower than
  the next-slowest endpoint.
- At 500 users: POST /api/authenticate reaches ~21 s p50 and ~34 s p95. Setup-heavy
  GET endpoints (exam-sheets setup, exams setup, questions setup) rise to ~10–12 s at
  p95 — still well below authentication.
- Simple CRUD reads (courses, exam-sheets, student-responses) remain below 200 ms p95
  at 500 users.

**Potential conclusions:**
Authentication is the single most significant performance bottleneck for this application
at load. The likely cause is synchronous JDBC lookup in the authentication path (user
credential verification + JWT signing) combined with a fixed-size blocking executor pool.
Under load, Locust users repeatedly authenticate at scenario entry, causing the auth queue
to build up dramatically. This is an important finding for the IaC paper: resource
provisioning cannot compensate for an application-level bottleneck. Any horizontal
scaling strategy would also need to address this endpoint specifically.

### Fig 8 — Throughput Heatmap
**File:** fig8_heatmap.png

**What it shows:** A matrix of measured throughput values (req/s), with VM configurations
as rows and concurrent user counts as columns. Grey cells indicate missing data (not
tested due to reservation ending). Numbers in cells are rounded req/s values.

**How to read it:** The colour gradient goes from light yellow (low throughput) to dark
red (high throughput). The horizontal progress of filled cells per row shows how far
the sweep reached for each configuration.

**What the data shows:**
- The 2cpu-4gb row is the only fully populated one (all 8 user-count columns).
- At any given user count where multiple configs have data, the values are almost
  identical: e.g., at u100 all five configs that were measured show 46–47 req/s.
- 2cpu-2gb extends to u500 (197 req/s). All other configs stop at u100 or earlier.
- The absolute throughput values are consistent: CPU and RAM count do not affect req/s
  at the same user load level, confirming the I/O-bound finding.

**Potential conclusions:**
This figure is the clearest single-slide summary of the experiment's current state. It
immediately communicates three things to an audience: (1) all tested configurations
perform identically at equivalent loads, (2) only two configurations have been tested at
high load, and (3) the data collection is work in progress. Ideal for a status-update
slide in an advisor presentation.

### Fig 9 — Resource Provisioning Efficiency
**File:** fig9_efficiency.png

**What it shows:** Two bar charts derived from the stable capacity envelope (max users
with p95 < 1 s and 0% failures):
- Left: stable users per vCPU, for the four CPU-varying configurations.
- Right: stable users per GB RAM, for the three RAM-varying configurations.
Hatched bars indicate partial data (lower bound); solid bars are fully confirmed.

**What the data shows:**
- CPU axis: 2 vCPUs gives 250 stable users/vCPU (confirmed). 1 vCPU gives ≥50
  users/vCPU (partial — reservation ended at u50). 4 and 8 vCPUs give ≥6 and ≥12 —
  also partial, and the low values reflect how few user-count steps were completed
  before the reservation ended, not true capacity.
- RAM axis: 2 GB gives 100 users/GB; 4 GB gives 125 users/GB (25% improvement in
  efficiency). 8 GB gives ≥3 users/GB (partial, very low because only u25 was completed).

**Potential conclusions:**
With the data confirmed so far, 2 vCPUs provides the best measured CPU efficiency.
4 GB RAM is more efficient than 2 GB (125 vs. 100 stable users per GB). Over-provisioning
RAM beyond 4 GB appears to yield diminishing returns (≥3 users/GB for 8 GB, though this
is a lower bound). The central IaC research question — what is the optimal resource
allocation for this workload class? — is partially answered: 2 vCPU / 4 GB appears to
be the sweet spot in the tested range, pending completion of the other configurations.

### Fig 10 — Response-Time Time Series (2 vCPU / 4 GB @ 100 and 1000 Users)
**File:** fig10_timeseries.png

**What it shows:** Time-series of p50 and p95 response time during a 5-minute Locust
run, for two load steps: 100 users (top, blue) and 1000 users (bottom, red). The
secondary axis (dotted grey) shows concurrent throughput in req/s over time.

**What the data shows:**
- At 100 users: There is a sharp latency spike in the first ~30–40 seconds as users
  ramp up (Locust adds users at 50/s, so full 100 users are reached in 2 seconds).
  After the ramp, both p50 and p95 stabilise at low values (~8 ms p50, ~75 ms p95).
  The spike is attributed to JVM JIT warm-up effects — initial requests hit the
  interpreter, subsequent ones hit compiled code.
- At 1000 users: The ramp phase (~20 seconds) drives latency to a peak of ~25 000 ms
  p95 as 1000 users flood the system simultaneously. After the ramp, the system
  partially stabilises but at much higher latency (~1 500 ms p50, ~5 000 ms p95),
  reflecting sustained queue depth.

**Potential conclusions:**
The warm-up effect at u100 is a methodological note: the first 30 seconds of any load
step inflates latency artificially. If this is important for the paper's validity, the
scenario should be extended with a warm-up period excluded from statistics. At u1000,
the system never fully recovers to stable steady state within the 5-minute window,
indicating that 1000 users is beyond the comfortable operating range for 2cpu-4gb.

### Fig 11 — Stable Capacity Envelope per VM Configuration
**File:** fig11_stable_envelope.png

**What it shows:** Bar chart showing, for each configuration, the maximum number of
concurrent users at which the system maintained p95 < 1 000 ms and 0% failure rate.
Hatched bars are partial (lower bound); solid bars are confirmed.

**What the data shows:**
- 2cpu-4gb: confirmed stable at 500 users (the last step before p95 exceeds 1 s is u500
  at 830 ms p95).
- 2cpu-2gb: confirmed stable at 200 users (u500 gives 1 100 ms, crossing the threshold).
- 2cpu-8gb: ≥25 (partial — reservation ended after u25 with 0% failures).
- 1cpu-4gb: ≥50 (partial).
- 4cpu-4gb: ≥25 (partial — only u10 and u25 completed before crash at u50).
- 8cpu-4gb: ≥100 (partial — stable at u100 with 59 ms p95, crashed at u200).

**Potential conclusions:**
The two confirmed data points tell a concrete story: doubling RAM from 2 GB to 4 GB
increases stable capacity from 200 to 500 concurrent users — a 2.5× improvement in
capacity for a 2× increase in cost. This is the kind of evidence an IaC paper needs.
The partial configurations indicate that more testing is needed to determine whether
adding CPUs beyond 2 or RAM beyond 4 GB provides additional gains. The hatching makes
the uncertainty explicit without hiding the lower-bound values.

### Fig 12 — Throughput vs. Provisioned Resources (Bubble Plot @ 100 Users)
**File:** fig12_scatter_resources.png

**What it shows:** 2D scatter plot with vCPUs on the x-axis and RAM (GB) on the y-axis.
Each bubble represents one configuration; bubble size and colour encode throughput (req/s)
at 100 concurrent users.

**What the data shows:**
- Only three configurations have valid u100 data: 2cpu-2gb (46 r/s), 2cpu-4gb (47 r/s),
  and 8cpu-4gb (47 r/s).
- All three throughput values are essentially identical (~47 req/s). Bubble sizes and
  colours are nearly the same.

**Potential conclusions:**
This figure confirms visually what Figs 1 and 3 already show: at 100 users, provisioning
more CPU or RAM does not yield more throughput. The three bubbles could be the same size
regardless of their position on the resource axes. When the missing configurations
(1cpu, 4cpu, and 4 GB vs. 8 GB comparisons at higher load) are filled in during the
next reservation, this figure will become more informative.

## Recommended Figures for Advisor Presentation

The full set of 12 figures is suitable for a technical paper appendix. For a
work-in-progress advisor meeting, 5 figures covering the key findings is more appropriate.
Below is the recommended selection and the narrative order to present them.

---

### Slide 1 — The Experiment at a Glance
**Use: Fig 8 (Heatmap)**

Open with this. It immediately shows the full experimental matrix: 6 configurations × 8
user-count steps, with grey cells for data not yet collected. The audience understands
the scope of what has been done and what is pending in one slide. Say: "Each cell is a
5-minute Locust load test. We have partial data due to reservation expiry — a second
run will complete the missing cells."

---

### Slide 2 — The Full Saturation Story (Reference Config)
**Use: Fig 5 (Saturation Profile — 2 vCPU / 4 GB)**

This is the deepest result. Present the two-panel figure: throughput plateau at 200 req/s
followed by collapse, and the percentile fan opening up dramatically beyond u500. This
is the clearest illustration of IaC provisioning impact — you can directly read the
capacity limit of one configuration off this graph. Say: "This is our most complete
configuration. The system saturates at 500 concurrent users. Beyond that, latency
becomes unacceptable. Our IaC patch generator needs to know this ceiling."

---

### Slide 3 — RAM vs. CPU: What Actually Matters
**Use: Fig 3 (Throughput — CPU Effect)**

This is the counter-intuitive finding and likely to generate discussion. Four different
CPU allocations (1, 2, 4, 8 vCPUs) produce almost identical throughput at the same
concurrent user count. Say: "Adding CPUs does not improve throughput for this workload
class. The bottleneck is the database I/O path, not computation. This has direct
implications for how an IaC recommender system should prioritise resource dimensions."

---

### Slide 4 — Where Configurations Diverge: The Capacity Ceiling
**Use: Fig 11 (Stable Capacity Envelope)**

Now show how the two confirmed configurations compare: 2 GB stable at 200 users, 4 GB
stable at 500 users. The hatched bars make clear which values need more data. Say:
"Doubling RAM from 2 to 4 GB delivers 2.5× more stable concurrent-user capacity. The
cost-to-capacity ratio improves with RAM for this workload, up to the point tested.
The hatched bars are lower bounds — our next reservation will confirm them."

---

### Slide 5 — The Hidden Bottleneck: Authentication
**Use: Fig 7 (Endpoint Latency Breakdown)**

End with this because it opens the discussion for future work. Authenticate takes 7–34 s
at p95 while all other endpoints stay below 500 ms. Say: "Even with optimal
infrastructure provisioning, this application has an application-level bottleneck.
Authentication latency dominates under load. No IaC change can fix this — it requires
a code change. This highlights an important limitation of pure infrastructure-level
optimisation, which is relevant to the paper's threat-to-validity section."

---

### Optional Slide 6 (if time allows)
**Use: Fig 9 (Resource Efficiency)**

Add this if the advisors ask "so what is the optimal configuration?" It gives the
answer in concrete terms: stable users per provisioned resource unit. The IaC angle
is direct: an automated patch generator targeting this efficiency metric would recommend
2 vCPU / 4 GB over 8 vCPU / 4 GB for cost-performance balance.

---

### Figures to omit from the presentation (keep for paper appendix)
- **Fig 1, 2** (RAM throughput/latency): the story is better told by Fig 11.
- **Fig 4** (CPU latency): same story as Fig 3 but less striking visually.

## What is Missing and What to Do Next

1. **Re-run 5 configurations** on the next Grid5000 reservation (with the deployment
   fixes already committed): 2cpu-8gb, 1cpu-4gb, 4cpu-4gb, 8cpu-4gb, and ideally
   also 2cpu-2gb at u1000 and u2000 to get a full saturation curve for comparison.

2. **Two configs definitively failed at startup** (2cpu-512mb, 2cpu-1gb). This is a
   valid experimental result: the minimum viable provisioning floor for this application
   stack is above 1 GB RAM. Document this as a finding.

3. **Authentication bottleneck** is an application-level issue, not an IaC issue.
   If the paper needs a clean IaC story, consider pre-warming the JVM and auth cache
   before running the load test, or excluding the auth endpoint from saturation
   calculations to isolate the IaC effect.

4. **Prometheus / Grafana metrics** (JVM heap, CPU utilisation, MySQL query throughput)
   were not captured in these results because Prometheus scraping was not configured
   for all runs. When re-running, verify that Prometheus is scraping the VM's node
   exporter before Locust starts.
